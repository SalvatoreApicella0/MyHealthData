# Sync protocol v2 (current slice)

The legacy-compatible encrypted endpoint supports vault creation, enrollment, device tokens, idempotency keys, a monotonic cursor, and `upsert`/`tombstone` envelopes. A retry with the same idempotency key returns the original cursor. Revoked devices are rejected. These properties are tested in `sync-server/hub.test.mjs`.

The Hub REST measurement slice uses stable client IDs, `createdAt`, `updatedAt`, `originDeviceId`, `provenance`, integer `revision`, and `deleted`. A write with a mismatching `baseRevision` is rejected as `409 conflict`; deletion produces a tombstone. No client should treat a missing record as a deletion.

The device-only LAN listener permits `POST`/`GET /api/v1/sync/measurements`, `DELETE /api/v1/sync/measurements/{id}`, and a single pairing claim. Requests carry a device ID, a device token, a current timestamp, `X-MHD-Body-SHA256`, and an Ed25519 signature over the request method, path, idempotency key and body digest. The Hub recalculates the digest before authorizing a mutation, so a captured signature cannot be replayed with changed health values. A device can update or delete only records it originally created. For an existing device-owned record, `baseRevision` is mandatory on both update and deletion; a stale or omitted revision is rejected with `409`, leaving the server record unchanged. Clients retain a local content fingerprint and the last confirmed revision per uploaded record, so an interrupted create, update or delete can be retried safely after reconnecting.

The measurement slice is now the `measurements` case of a generic record store. Every `MHDDataSnapshot` domain replicates through `/api/v1/sync/records/{domain}` (signed device) and `/api/v1/records/{domain}` (loopback browser/administration), with the same stable IDs, `createdAt`/`updatedAt`, `originDeviceId`, `provenance`, integer `revision` and `deleted` tombstones as measurements. A signed write with a mismatching or missing `baseRevision` on an existing device-owned record is rejected with `409`; a device can only mutate records it created. `GET /api/v1/records/{domain}?since={cursor}` returns the revision/tombstone change log, while a request without `since` returns current state. Record payloads are bounded (64 KiB per record) and the domain name is restricted to an identifier pattern so an untrusted client cannot create unbounded collections. The existing measurement endpoints remain as aliases of the `measurements` domain, so build 66 clients keep working. `hub-state.json` migrates in place from schemaVersion 1 (measurement-only collections) to schemaVersion 2 (`records[domain]`) on open, preserving cursors, revisions and tombstones.

The standalone-to-Hub migration remains explicit and resumable work: it must upload canonical records with stable IDs and retain the local vault until semantic verification succeeds. The Web vault applies Hub changes to the same domains it can already write, and keeps local records the Hub does not mention (a missing record is not a deletion).

Attachments are intentionally outside the JSON record envelope. A paired client uploads the decrypted file bytes from its local vault to `POST /api/v1/sync/attachments/{attachmentId}` using the same timestamp/body-hash/signature headers as record writes, plus the content type, original name and SHA-256 headers. The loopback Web UI uses the matching unsigned `POST /api/v1/attachments/{attachmentId}` endpoint when a document is created or updated in the browser, then publishes the document record through `/api/v1/records/documents`. The Hub limits files to 16 MiB, verifies the declared hash, writes atomically, and exposes them to the loopback Web UI at `GET /api/v1/attachments/{attachmentId}`. Missing attachment bytes never delete or invalidate the document metadata; the Web UI reports the file as unavailable and keeps the record usable.
